## 2. 平台限制（已查证，设计以此为准）
- 新 bot 建好后，平台会自动给它一轮首次运行，提示它先问候用户，还提示不要读 profile 文件（参谋长创世第 0 节的设定核对不受这句限制）。
- 建 bot 只能设名字和设定正文（另有侧栏分组参数，本流程不用）；改 bot 只能改名字和设定正文。一个 bot 只有一份设定正文，不能拆。描述为权威。
- 不能替别的 bot 写记忆、建定时任务、装插件。定时任务只能由 bot 给自己建。
- 模板不能用程序导入，只能把模板链接发给用户，由用户导入。模板导入不装私有 skill，开场引导也不触发（实测 2026-10-16）；模板带不了脚本。
- skill 全局共用，全机只有一份，任何 bot 都能写，不能锁定给参谋长，也没有版本号。新 bot 看到的 skill 列表会截断：判断本机有没有某个 skill 只看 /home/box/agent-data/workflows/*/SKILL.md 的 frontmatter name。skill 用英文名保存后 skill-id 就是这个英文名，按英文名可以加载；按中文名加载会失败（2026-10-20、10-21 实测）。本流程四个 skill 的 name：flow-onboarding（上手）、flow-genesis（创世）、flow-chief-governance（参谋长治理）、flow-general（通用流程）。本机名字是旧中文名的那份（更早版本装的）check.py 也认得，报落后或被改过。
- UpdateSkill 的正文只能内联传入，装完必须用 `build/hash.py` 和克隆核对。
- 定时任务按北京时间的 cron 执行，前后浮动约 15 分钟；能读写本机文件（2026-10-20 实测）；指令里不写工具名。
- 子代理（后台子任务）的记录，主 bot 事后读不到。
- 应用连接挂在用户账号上，授权一次后所有 bot 共用；bot 能查连接状态，安装要用户确认，授权不能跳过。
- **台账写权限无法按 bot 隔离**：所有 bot 是同一个系统用户，环境里也没有 bot ID。ledger.py 核对自报的 bot ID 和名册，只防误写，防不住冒名（用户 2026-10-20 认可）；靠修改记录留痕和巡检对照对话记录。
- 设定正文平台上限约 20000 字符，超长会被静默截断，建 bot 后用哈希核对；skill 按职责拆开；模板、skill 大小上限未查到。
- 平台 bot 列表只能看本机 `/home/box/agent-data/agents/*/profile.json`，去掉 `/home/box/sand-data/deleted-agents.json` 里的 ID；在侧栏删掉的 bot 目录可能还留着、也不一定进删除记录（2026-10-20 见到一例，含义未查证），所以名册里没有的只报给用户定。
- 读其他 bot 设定正文=读该 bot 的 profile.json 的 description；id 即目录名/CreateAgent 返回值；不能给已有 bot 开无上下文会话（共用 bot 靠派活单隔离，红队用无上下文临时子任务、不建 bot）；shared_* 记忆跨 bot、本地记忆分 bot。
- 能读用户名下其他 bot 的对话记录（ReadTranscript，按 agent_id，从最新往前分页）；bot 被删后记录也一起删掉。别的 bot 的本地记忆没有直接读的办法，只能从记录里平台注入的记忆片段看到一部分，或请它自己列出。
- 用 UpdateAgent 改设定后：bot ID 和名字（没改名时）不变，改前写入的 profile 记忆、已暂停的定时任务都还在，对话记录不变，这个 bot 能用 ReadTranscript 从头读完自己的记录（2026-10-21 实测，流程治理 F-2）。正在运行的定时任务等其他情况没实测过。

## 4. 修改 skill、模板、脚本（治理增量）
按第 1 节当一个任务走（属于大变更的另按第 4d 节）；不按变更三级分，错别字也走完整流程（skill「flow-general」（通用流程，`/home/box/flow-repo/skills/general-flow/SKILL.md`）第 4 节的微调白名单不适用于 skill、模板和脚本）。用户要你改、但明确拒绝走完整流程（如「别搞那一整套」）时：不改、不起任务；说明为什么不能跳过，把这件事记成候选（第 1 节），等用户明确同意起任务。开始改之前先跑检查脚本（第 11 节），确认本机与克隆当前 tag 一致。
- **任务步骤**：澄清 → 设计 → 无上下文红队评审（由参谋长开无上下文临时子任务，不建 bot；给的材料只有两样：用 git 生成的完整 diff 文件 `git -C 〈改动所在的工作目录〉 diff --no-color 〈当前 tag〉 > /home/box/flow-data/流程治理/runs/红队-〈日期〉.diff`，原样整份交给子任务，不摘录、不删减、不加导读；再加上被改文件的全文。不附参谋长自己的结论或改动理由）→ 压力测试和触发测试（见下）→ 影响面征询（第 4b 节）→ 锁标准 → 开发 → 专职·流程QA 验收。
- **压力测试和触发测试**：改 skill 或 bot 模板时，针对改动涉及的规矩写 3 个以上叠加压力（赶时间、沉没成本、用户或权威施压、疲劳、「这次情况特殊」）的开放式场景：不给选项，提示里不写规矩原话。有 skill 和无 skill 对照各跑 5 次以上，每次用全新的无上下文临时子任务，人工读每个答案，下一步动作违规也算不合格。无 skill 对照本来就合格的规矩，不必为它加措辞。改了描述的再做触发测试：每个受影响 skill 8 条该触发、8 条不该触发的真实请求，把各 skill 的名称和描述原文列成目录写进提示（不加载 skill，名称用中文也不影响），混进本机其他 skill 的描述，让无上下文子任务选会先读哪些，召回 ≥7/8、误触发 ≤1/8 才算过。结果原样附进验收材料。题目、跑法和评分都用仓库里的 `tests/`（见 `tests/README.md`）：`python3 〈被测仓库〉/tests/run.py all --suite both --reps 3`，新改的规矩先往 `tests/pressure/scenarios.json` 加题再跑；附上 `结果.md`、和上次结果的 `compare` 输出、`manifest.json` 里的提交号。

5. 算发现的：
   - 没按流程做：跳过关口、规则被改动或本机与仓库不一致、派活单缺派出或回执时间、待确认积压超过 10 条或 3 天、拿非「用户已确认」的标准判定、转述而不是原样附脚本输出或专职·流程QA 回执、台账写入者不是该项目副官、写入找不到主对话里的调用；
   - 备份未推成功超过 1 天；
   - 摩擦：用户反复纠正同一件事、用户不满、同一项反复返工、已定的事被重新打开；
   - 未验证就交付：链接、文件、结论没有证据就交给用户；
   - 卡住：工具被拦、权限不足、环境报错、派活超时没回执；改造跟进 R（第 7.5 节第 4 项）过了期限还没登记名册；
   - 分工失衡：检视副官 D 表里「自己做还是拆给专职 bot」的判断记录，看副官是否因自己做太多而疏于管流程（如关口、派活、回执登记滞后），或判断没记 D；
   - 可通用的改进点：多个副官遇到同一个问题。
5b. 摩擦：跑 `L frictions --since 〈窗口开始日期〉`（只读，跨名册所有库按节号汇总 M 表），终端输出原样附进报告。同一节号在窗口里 2 条以上或来自 2 个以上项目的，算一条发现（类型「摩擦」），证据写全部「项目 M-n」；单条的不报，留给周复盘。
6. 每条发现写：bot、一行证据（带位置）、提议，提议标类型：`skill` / `bot`（改设定正文）/ `routine` / `表`。
7. 报告按 bot 分组，结尾请用户勾选采纳哪几条。没有值得提的就不发，不写「一切正常」。
8. 巡检只提议，不改任何东西；用户采纳后按类型执行：`skill`、模板、脚本按第 4 节；`bot` 改设定按第 8 节，建新 bot 按第 7 节；`routine`（改定时任务）由参谋长发消息让对应 bot 自己改，下次巡检核对；`表`（改表结构）由参谋长在「流程治理」里起任务按第 4 节改。

## 6. 每周一复盘（定时任务，没事不出声）
1. 摩擦汇总：跑 `L frictions`（不带 --since；已进候选的默认不列），终端输出原样附上。同一节号累计 2 条以上或涉及 2 个以上项目的，合并记成一条候选 D，来源写全部编号（`记账 M-3, 旅行 M-1` 这种「项目 M-n」写法，逗号分隔）；写进来源的以后就不再列，用户否决的也一样。单条的留着继续观察。只关系一个项目、不是规矩本身问题的，交该项目副官处理。
1b. 汇总上周发现和副官建议，按第 1 节记成候选（同一根因合并）；只对单个项目有用的交该项目副官记进它的 D 表（参谋长不写副官的台账），不进 skill；够格的起任务按第 4 节走。
2. 定时任务检查（各 bot 的，包括参谋长自己的三个；别的 bot 的定时任务你读不到，发消息请它原样贴出自己的定时任务名称、时间和指令，没回的标「未核实」）：指令对不对得上 `templates/routines.md`（填好 bot ID 后逐字比），时间对不对得上用户确认过的时间（创世清单、立项消息或之后用户改时间的 D 条；没改过的就是 routines.md 的默认时间）；频率过高、挂在很长的对话上、空跑也发报告、目标已不在或一直报错、重复；已归档项目的副官是否删掉了自己的定时任务。找不到记录只能从对话推断的，标「未核实」。
3. 电脑状态：内存、长时间运行的进程、本地服务，列出可清理的候选，停之前先问用户。
4. 名册：核对状态、定时任务，标出可以退役或合并的 bot。
5. 没有可提的就不发。

## 7. 建 bot
### 7.1 共同标准
- 需求来源：副官提需求，或巡检、复盘发现缺口；分工规则见 skill「flow-general」（通用流程，`/home/box/flow-repo/skills/general-flow/SKILL.md`）第 12 节。按第 1 节当一个任务走（创世例外见 skill「flow-genesis」（创世，`/home/box/flow-repo/skills/genesis/SKILL.md`），仅限创世那一次确认）。第一个副官例外：按第 7.1a 节，用户批准即可，不走完整任务；之后的副官照常当任务走，立项时的了解范围和交接单格式同第 7.1a 节第 1、3 步。
- 命名：副官叫「副官·项目名」；参谋长叫「参谋长」；参谋长建的共用专职 bot 叫「专职·角色名」（如专职·流程QA、专职·想法挑刺）；模板库导入的保留原名。共用专职 bot 不绑项目，项目间靠派活单隔离，设定里不写绑定某个项目的措辞。
- 设定正文包括：唯一职责（说不清就拆开或不建）、不做的事（每条都写进设定正文）、一种口吻、只用职责用得上的应用、核心规矩、要建的定时任务和建的时机、首次运行只说一句（`templates/README.md`）、「有已连接且能用的应用就优先用应用，授权从不跳过」。副官和参谋长例外：设定正文只写定位，规矩全在 skill（见 `templates/README.md`）。平台上限约 20000 字符，超长会被静默截断，建 bot 后用哈希核对；细节放 skill。
- 创建前查用户账号连接状态，必要应用全部连好才在名册登记「在用」；可选应用到要用时再提醒。用户批准后才创建，不单独试跑。

### 7.1a 第一个副官交接（创世之后第一个想法）
1. 用户说出第一个想法后，你判断要不要立项。只按第 0 节做大致了解：以用户的话为主；用户给了资料位置的，最多看目录列表和顶层说明文件，不拷贝、不细读；资料在用户电脑上的，不列目录、不读、不拷。一条消息给用户：建议项目名、副官名「副官·〈项目名〉」、理由、已有资料位置（照用户说的写，只写路径或取用方式）、要连的应用（按 `templates/README.md`）、副官每日扫描的时间（默认取 `templates/routines.md` 第 4 节）。项目名单独一行请用户确认（名册的「所属项目」「库路径」和项目库都绑定项目名，建好后不改）。问「就这样立项吗？」。
2. 用户确认后：
   1. CreateAgent，设定用克隆当前 tag 的 `templates/deputy.md` 填好项目名，读回 profile.json 用 `build/hash.py` 核对。

   3. 平台会自动让新副官首轮问候；按模板它只说一句「等参谋长交接」。
   副官 `L init` 被拒（比如个人信息检测）时会把报错原文回给你：名册行不动，改好交接单重发。
3. 把交接单写成文件 `/home/box/flow-data/流程治理/runs/〈YYYYMMDD-HHMMSS〉-〈你的 ID 前 8 位〉/handoff-〈项目名〉.json`：
   ```json

   交接单文件只放上面这几栏（`L init` 只认这些字段），「已有资料位置」只写在下面的消息里。
   想法原话会写进副官库 D-1（核心列，之后不能改，随备份推到 GitHub）：银行卡、证件、家人、住址等原文不放进去，用中性说法加共享记忆引用代替。`L init` 被个人信息检测拒绝时，改写交接单再跑，不加 `--pii-checked` 硬写（确实不含原文时例外，按 skill「flow-general」（通用流程，`/home/box/flow-repo/skills/general-flow/SKILL.md`）第 2 节）。

   ```
   交接单只写上面这些栏；除「参谋长概括」那最多两句外，不写项目细节（从资料细节里读来的内容、你对项目的分析、建议怎么做）。拷贝资料、读资料、从资料里整理事实和决定都由副官自己做；资料在用户电脑上的，跨机读取或拷贝由副官向用户发起，要用户在他电脑上批准。

### 7.5 已有 bot 改造成副官
用户对参谋长说要把某个已有 bot 纳入流程时用。和第 7.1a 节新建副官是同一套流程，区别在于：不新建 bot，而是把这个 bot 的设定改成副官设定；另外多发一份改造通知（第 4 项）、记一条改造跟进 R（第 4 项），名册推迟到第二次确认之后才登记（第 5 项）。你的活到「把它改成能按副官流程走的 bot」为止（第 0 节）：只读它现在的设定正文，不读它的对话记录和项目资料，不起草它的台账，不处理它的记忆和定时任务；这些都由改造后的副官按 skill「flow-general」（通用流程，`/home/box/flow-repo/skills/general-flow/SKILL.md`）第 1 节「由已有 bot 改造的」自己做，由它经 ledger.py 写库，你不写它的库。用户批准即可，不走完整任务（第 0 节）。分两次确认（用户 2026-10-21 定，流程治理 D-6）：第一次确认立项和新设定，由你交（第 3 项）；第二次确认台账初稿，由副官先交专职·流程QA 核对、再交用户。名册在第二次确认之后才登记（第 5 项），从改设定到登记名册之间它不在名册里、也没有库，是预期的。改造前和改造中都不删这个 bot（删了对话记录也一起删掉，副官就读不到历史了）；改设定后它的对话记录不变，改前写入的 profile 记忆、已暂停的定时任务都还在（第 2 节，F-2）。
1. **判断立项**：按第 7.1a 节第 1 步，根据用户要求改造时的消息判断立项，起项目名和副官名（按第 7.1 节命名，用户可以不改名）。只用用户的话和这个 bot 的名字、设定正文，不为此读它的对话记录。
