# 通用流程 v0.0.1

**每过一个关口，先重读本 skill 里对应的章节**（关口一读第 5、6 节；关口二读第 7 节；执行前关口读第 8 节；关口三读第 9 节；机械检查读第 10 节；派活读第 11、12 节；出口和运营轮读第 14、15 节）。副官和参谋长都先遵守第 0 节「副官守则」（原设定正文的通用条目，设定正文只写定位）。参谋长的治理工作见 skill「参谋长治理」；各 bot 的设定正文见 skill「固定bot设定」。

本文中「用户」指项目所属的人。副官指每个具体项目的主 bot；参谋长是特殊的副官：它就是「流程治理」项目的副官，同样按本流程走，另加治理增量（见 skill「参谋长治理」），是唯一负责修改本 skill 的 bot。副官、专职·流程QA、专职·想法挑刺、专职 bot、检查脚本都按名称称呼。

## 0. 副官守则（副官和参谋长都必须遵守；设定正文只写定位，规矩全在这里）
- 你按本 skill 推进项目，每过一个关口先重读本 skill 里对应的章节。
- 第一次对话时，你先给自己建一个每日定时任务：按第 10 节做全部机械项（跑检查脚本，人工查第 1–11 项），只有第 10 节列的四类问题才找用户，否则不出声。（参谋长不建这一个，按 skill「参谋长治理」第 0 节建三个。）
- 你是唯一能写本项目表的 bot，其他 bot 只交草稿或回执；表只增不删，核心列写入后不改，要改就新建一条并标记旧条目。
- 你自定的决定先标「生效（待用户确认）」交用户确认。
- 变更按被改对象机械定级：动到「必须」级标准、目标、约束或用户拍板的决定一律算大变更并退回澄清，拿不准往高一级定。
- 关口判定只依据「用户已确认」的验收标准、检查脚本原始输出和专职·流程QA 原始回执，原样附上，不转述；标准由专职·流程QA 起草、你审、用户确认后你写表。
- 每一步交出去之前都过关口二，第 1、3、6 项不能省。
- 派活一律用固定派活单并填派出时间，收回执后填回执时间，并至少独立复核一条「必须」级标准。
- 不可逆步骤必须先经专职·流程QA 预审、再经用户确认才能执行，证据留执行前快照和执行回执。
- 同一 A 编号累计失败 3 次，或关口三回退到第 3 轮，你停下找用户。
- 不能裁剪的最小集你不提议裁剪；用户偏好经用户同意才写进共享记忆。
- 负责否决的角色交独立 bot；其他工作按量自己做或拆给专职 bot，判断理由记进 D 表。
- 你只管本项目（例外：跑检查脚本时只读「流程治理」脚本维护表的检查脚本在用行，见第 10 节「检查脚本」）；不改 skill、不做治理，流程改进建议和新 bot 需求一律交给参谋长。（参谋长例外：治理按 skill「参谋长治理」执行。）
- 有已连接且能用的应用就优先用应用，需要授权或安装时先问用户，授权从不跳过。

## 1. 适用和入口
- 副官判断要不要建项目并给理由，建或不建都交用户确认。
- 建项目时：建好 F、D、R 三张表、设计文档 S、P 表、A 表、检查日志；把本 skill 版本号记成一条 D。
- 新建：用户的想法记成第一条 D，隐含前提记成「待查证」的 F。
- 接手：已有事实标「待查证」；已有决定原样录入，理由写「接手时已存在」；列现状清单，由用户决定从哪个阶段接着走。
- 问清期限、预算、地区和收款限制、哪些事必须用户亲自做。共享记忆里已有的不再问，但必须在 D 表登记（来源写「共享记忆 + 日期」）。
- 裁剪：不能裁剪的最小集见第 13 节。不做现成裁剪包；最小集以外的部分由副官逐项提议，每项写清「裁掉后少了什么保障」，用户逐项确认后才生效。

## 2. 对象清单
| 对象 | 载体 | 编号 | 只增不删 | 核心列（写入后不能改） | 谁写 |
|---|---|---|---|---|---|
| 事实/假设表 F | Notion 数据库 | F-1 | 是 | 内容 | 副官 |
| 决策表 D | Notion 数据库 | D-1 | 是 | 决定、理由 | 副官 |
| 风险表 R | Notion 数据库 | R-1 | 是 | 风险、对策 | 副官 |
| 设计文档 S | Notion 数据库，一节一条 | S-1 | 是 | 结论 | 副官 |
| 实施计划表 P | Notion 数据库 | P-1 | 是 | 完成标准（A 编号文本）、自验证方式、可逆性 | 副官 |
| 验收标准表 A | Notion 数据库 | A-1 | 是 | 标准、依据、级别、检查方法、版本号 | 副官（专职·流程QA 起草） |
| 检查日志 | Notion 页面 | 按运行时间 | 是 | 全部（脚本原始输出） | 跑检查脚本的 bot 原样贴入，不得改动 |
| 模板表、bot 名册、skill 维护表、脚本维护表（只在「流程治理」项目里） | Notion 数据库 | T-1 / B-1 / K-1 / J-1 | 是 | 见 skill「参谋长治理」 | 参谋长 |

执行依据 = 一份设计文档 S + 两张表 P、A。S、P、A 的每一条都用关联属性标注依据编号，对不上就先补表。

### 通用记录规则
- 依赖只记上游：用 Notion 关联属性，按目标库分别建（如「依赖F」「依赖D」）；下游列表由工具自动生成，不手写。
- 核心列写入后不能改：要改就新建一条，旧条目标「作废 / 已推翻 / 已合并」。标准措辞改动也按核心列改动处理。
- 默认视图用筛选排除作废、已推翻、已合并的条目；另建「按状态分组」视图看历史。
- 只有副官能写表；其他 bot 只交草稿或回执；检查日志只放检查脚本的原始输出，由跑脚本的 bot（「流程治理」里是参谋长，其他项目是本项目副官）原样贴入，不得改动。
- 加依赖、做复查都要用户确认（走第 4 节确认机制）；可攒批一屏确认，不逐条打断。

## 3. 表结构和状态
### F 事实/假设表
- 列：内容、状态、来源、查证日期、有效期、有效期依据、依赖、说明
- 状态：待查证 / 已查证 / 已查证（二手）/ 已过期 / 需复查 / 已推翻 / 已合并
- 只放客观事实，以一手直接证据为准。
- 查不到一手来源时可用二手，标「已查证（二手）」，说明里写试过哪些一手渠道和结果。
- 关键事实：凡沿依赖链被 S 第 1 节（目标）或任何「必须」级标准依赖到的事实，按依赖链机械认定（第 10 节机械项 3，人工检查），不设「致命」列。关键事实只有「已查证」（一手）才算通过。
- 有效期顺序：常识和定律标长期有效 → 政策规则查其自身写明的有效期 → 查不到就估一个并写依据 → 最后用这一类的默认值。
- 说明：待查证的写为什么暂时相信、准备怎么查；被推翻的写推翻依据。
- 过期扫描：属于每日扫描（见第 10 节），新增事实时、每过一个关口时各再扫一次。

### D 决策表
- 列：日期、决定、理由、来源、依赖、谁拍板、状态、作废理由、类型（决定 / 候选；候选只在「流程治理」项目用，见 skill「参谋长治理」第 1 节）
- 状态：生效 / 生效（待用户确认）/ 待定 / 需复查 / 作废 / 已合并 / 已否决 / 历史决策（创世或接手时已定、不走完整任务补录的）
- 用户的偏好、预算、限制等主观内容记在这里。
- 从共享记忆引用的偏好必须登记一条，来源写「共享记忆 + 日期」，并列进关口一的一屏拍板。
- 比较过的备选写在理由里；某备选被反复提起才单独记一条，标「已否决」。
- 只依赖「待查证」事实的决定，状态最多是「待定」。

### R 风险表
- 列：风险、依赖、可能性（高/中/低）、影响（高/中/低）、对策、负责人、状态、说明
- 状态：监控中 / 已发生 / 需复查 / 已消除 / 已合并
- 影响为「高」的必须有对策；每过一个关口过一遍风险表。

### S 设计文档（只写结论）
- 四节，每节一条数据库条目，带依赖关联：1 目标和边界；2 对象和场景；3 方案（按模块写，模块划分由用户确认）；4 约束（硬约束只在此节列出）。
- 状态：生效 / 需复查 / 作废

### P 实施计划表（兼调度表）
- 列：步骤、依据、前置、执行人、完成标准（A 编号文本，如「A-3」，不带版本号）、自验证方式、可逆性（可逆/不可逆）、派出时间、回执时间、截止、状态、说明
- 状态：未开始 / 进行中 / 挂起 / 自验证中 / 需复查 / 已完成 / 已作废
- 前置步骤都已完成才能开工；无前置关系的步骤可并行。
- 自验证方式可以比检查方法更细，不能更松（判断项，由 专职·流程QA 起草标准时一并审）。
- 不可逆步骤（发消息或邮件、部署、删数据、批量改线上配置、付款、提交申请等）执行前必须过执行前关口。

### A 验收标准表
- 列：标准、依据、级别（必须/可延后）、检查方法、检查人、版本号、状态、证据、说明
- 状态：草稿 / 用户已确认 / 需复查 / 已被取代 / 作废
- 专职·流程QA 起草 → 副官审 → 用户逐条确认 → 副官写表。
- 只有「用户已确认」且为在用版本的条目能当判定依据。A 表不记哈希，靠状态和版本号管理：一条标准以 A 编号 + 版本号定位；用户已确认的标准要改，就新增一行（同一 A 编号、版本号递增，从起草重走到用户确认），新行确认后旧行改「已被取代」；同一 A 编号只能有一行「用户已确认」，即在用版本。P 表、派活单、回执都按 A 编号引用，判定时一律取该编号的在用版本。P 表「完成标准」存 A 编号文本，是核心列；另建到 A 表的关联属性只作导航，不算核心列，新版本确认后可改指在用行。
- 能判断是或否才算标准；主观口味只能由用户判断。
- 证据必须带版本号（文件哈希、提交号或 Notion 版本时间）；不可逆步骤证据为「执行前快照 + 执行回执」（消息 ID、交易号、照片等）。
- 探索型任务可以先写过程标准（如「至少比较 3 个方向，每个都有一手证据和结论」），结束时补结果标准，按中等变更处理。
- 每条「必须」级标准至少被一个 P 步骤引用。

## 4. 确认、变更、挂起、失败
### 确认机制
- AI 自定的决定都要用户确认，不设「只知会」类；可以攒批确认；用户改了就变成用户拍板。
- AI 自定的决定先以「生效（待用户确认）」生效：依赖它的步骤可开工，但不能过关口三。
- 用户否决时：副官按依赖链找出全部下游（机械项 2，人工检查），一律标「需复查」，对应 P 步骤退回「未开始」，已有证据作废。
- 积压上限：待确认超过 10 条，或最早一条超过 3 天，副官必须立刻找用户。

### 变更分三级（按被改对象机械判定，拿不准往高一级定）
- 大：动到 A 表「必须」级条目、S 第 1 节或第 4 节、D 表「谁拍板=用户」的条目 → 退回澄清；受影响检查项按依赖链机械找出，只重查这些。
- 中等：改计划步骤、拆分或合并步骤、换执行人、改「可延后」级标准、探索型任务补结果标准 → 记一条 D，状态「生效（待用户确认）」。
- 微调（白名单）：错别字、格式、不涉及任何 A 编号的内部实现细节 → 当场改，记一条 D，进待确认队列。**微调不适用于核心列**；核心列里的错别字也走新建条目，并重新取得用户确认（A 表标准改动按第 3 节新增版本行）。
- 事实变更：旧条目标「已推翻」，下游按需复查传播；被推翻的事实若被目标或「必须」级标准依赖，按大变更处理。
- 不能靠「重新解释」标准措辞绕开变更。

### 需复查传播
- 事实过期或被推翻、决定被否决或作废时，副官把下游一路传到底（机械项 2，人工检查），全部标「需复查」。每日扫描发现事实被推翻的，先请用户确认，确认后再触发传播。
- 复查后结论没变：只更新查证日期、有效期（非核心列），说明里记复查日志，并记一条 D，状态「生效（待用户确认）」。
- 结论变了：新建一条，旧条目标「已推翻」，继续往下游传。

### 挂起
写明在等什么，并设好什么时候回来查。

### 失败上限
- **只在「提交复核」事件上计数**（关口二提交、关口三提交、专职·流程QA 抽检或判断提交、执行前关口提交）。同一版本交付物被检查脚本或每日扫描重复判不通过，不累计。
- 按 A 编号累计；步骤拆分、合并、改名、关口三修复步骤都继承原计数。
- 同一 A 编号累计失败 3 次，停下找用户。
- 关口三最多回退 2 轮，第 3 轮必须找用户。

## 5. 澄清设计计划
1. 澄清：不限轮数，一次可问多个问题，按依赖排序，能查到的不问。五条全满足才停止提问：目标一句话写清且用户确认；边界划清并列出不做什么；每个方案模块能写出结论、不用猜用户偏好；每条「必须」级标准能写成是或否的句子；剩余问题都已记成待定或待查证并满足关口一放行条件。
2. 查证。
3. 想法挑刺：任何项目都做，只调深浅，交专职·想法挑刺。
4. 战略展望：写清有明确终止还是长期运营、终止条件、可能的扩展方向。
5. 设计。
6. 请 专职·流程QA 起草验收标准；副官写 P 表（含执行人和可逆性）。
7. 过关口一。

## 6. 关口一：澄清结束
### 关口一的清零（机械判断）
- 允许留「待定/待查证」条目，但每条同时满足：(a) R 表有对应条目和对策；(b) 标明并关联「最晚在哪个 P 步骤之前解决」；(c) 列进一屏拍板，由用户逐条勾选放行。放行标记只能在用户确认后写入。
- 关键事实已查证（一手），或作为放行条目满足上面三条。
- 没有「需复查」；R 表没有「已发生」却未处理的。

### 关口一检查项
1. 机械检查通过并满足关口一清零；影响为高的风险都有对策；S、P、A 齐全并都标了依据；每条「必须」级标准都有 P 步骤引用。
2. 判断项（是否违反约束、自验证是否比检查方法松）由专职·流程QA 唯一给出回执，原样附上。
3. 用户逐条确认验收标准；没有「用户已确认」的标准不能过关。
4. 一屏交用户拍板（首行写「降级模式：是 / 否」）：结论、三个最大风险、需要用户做的步骤和大概耗时、待勾选放行条目、从共享记忆引用的偏好、裁剪方案、检查脚本原始输出。
5. 三种结果：继续实施；改方向退回澄清并作废旧决定；放弃直接走出口。

## 7. 实施验证循环和关口二
### 循环
1. 按 P 表开工。
2. 按执行人派活或副官自己做；派活用第 11 节派活单，填派出时间。
3. 收回执，填回执时间；副官至少独立复核一条「必须」级标准。
4. 不可逆步骤先过执行前关口（第 8 节）。
5. 过关口二。
6. 通过的标已完成；不通过的重做；同一 A 编号累计失败 3 次找用户。
7. 变更按三级处理；要等外部的就挂起。
8. 只在里程碑、阻塞、需要用户动手、待确认积压到上限时找用户。
9. 所有步骤完成、没有「生效（待用户确认）」的决定后，进入关口三。

### 关口二：自验证（每一步交出去之前都过，含交给用户执行的步骤）
| 项 | 通过条件 | 要留的证据 |
|---|---|---|
| 1 对标准（不能省） | 逐条列出该步关联的 A 编号，每条给是或否 | 每条结果 + 带版本的证据 |
| 2 对自验证方式 | P 表写的自验证方式全部执行过 | 执行记录 |
| 3 对事实（不能省） | 用到的事实都不是已推翻、已过期、需复查 | F 编号列表 + 当前状态 |
| 4 对依据 | 每个结论都能追到 F/D/S 编号 | 依据编号列表 |
| 5 对约束 | 不违反 S 第 4 节任一条 | 逐条对照结果 |
| 6 补齐表（不能省） | 新发现的事实、风险、决定都已登记 | 新建条目编号 |

- 第 2、4、5 项只在该步不产出新结论、不涉及约束时可省，省了在 P 表说明里逐项写依据（为什么不产出新结论、为什么不涉及约束）；参谋长巡检抽查。
- 派出去的步骤：副官收回执后至少独立复核一条「必须」级标准。
- 副官自己做的步骤：涉及「必须」级标准的，抽一部分交 专职·流程QA 抽检，每个里程碑至少一次。

## 8. 执行前关口（只针对不可逆步骤）
专职·流程QA 预审（内容、对象、范围、无法回滚时的影响）→ 用户确认 → 执行 → 留执行前快照和执行回执作证据。

## 9. 关口三：总验收
### 关口三的清零（完全清零，机械判断）
- F：被生效决定或交付物依赖的条目里，没有「待查证」「需复查」「已过期」；关键事实没有只靠二手来源的。
- D：没有「待定」「需复查」「生效（待用户确认）」。
- R：没有「已发生」却未处理的；「监控中」的，长期运营项目写明负责人并交接给运营，有明确终止的项目结项时转「已消除」或写「由用户接管」。
- 关口一的放行条目都已在到期步骤前解决。
- 验收前 7 天内被改成作废或合并的条目，在验收报告里单独列出。

### 关口三检查项
1. 「必须」级标准在最终交付物上整体重测，证据必须是这一版的；不可逆步骤的条目改为核对执行证据，不重测。
2. 专职·流程QA 靠派活单隔离：每次只拿本单材料（交付物、「用户已确认」的标准和检查方法），只据派活单独立判断，不看副官的推理和自验证结论。平台不能给已有 bot 开无上下文会话，这一点靠自律，残余风险登记 R 表。「检查人=用户」的条目、主观口味、对外发布的标准由用户判断。
3. 专职·流程QA 原始回执原样附进验收报告；副官比对 A 表状态和回执（机械项 8，人工检查），不一致就判不通过。
4. 满足关口三清零，机械检查全部通过。
5. 交付物 → 验收标准 → 设计 → 决定 → 事实，这条链一路对得上。
6. 不通过的项回到实施，生成修复步骤，每个过关口二，失败计数按 A 编号继承。回归默认只测不通过项和受影响项（按依赖链机械找出，bot 只能往里加、不能删），专职·流程QA 或用户提出时升级全量回归。最多回退 2 轮。
7. 用户验收时提出的新要求按变更处理。

输出：验收报告（含检查脚本原始输出、专职·流程QA 原始回执）、交付清单。

## 10. 机械检查清单
- 每过一个关口、每天扫描时都做。检查脚本读 Notion 全量导出，只查第 12 项（导出完整性）；「流程治理」里另做 skill、脚本、设定的哈希核对（见 skill「参谋长治理」第 11 节）。导出、运行、降级规则和结果写回只在本节「检查脚本」定义；**原始输出由跑脚本的 bot 按「结果写回」格式原样贴进检查日志页面，不得改动**，并附进一屏拍板和验收报告，不转述。第 1–11 项由人工按清单逐项检查：副官过关口和每日扫描时查，参谋长工作日巡检时抽查；一屏拍板和验收报告里写明查了哪些条目、结果如何。
- 快照：每次的导出目录保留不删，就是快照（Notion 不提供字段级修改历史）；人工查第 7 项时拿本次导出与上次导出对比。对比范围：各表核心列；A 表状态+版本号+确认日期；D 表状态+谁拍板；关口一放行标记。平台无法按 bot 隔离写权限，靠本检测。
- 每日扫描做全部机械项，只有这四类才找用户：已过期或 7 天内过期的事实；依赖已推翻或已过期事实的条目；超截止或派出后超时无回执的步骤；待确认积压超过 10 条或最早一条超过 3 天；没有就不出声。发现事实被推翻时先请用户确认，再触发需复查传播。

### 机械项（第 1–11 项人工检查，第 12 项由检查脚本判定）
1. 依赖了已推翻、已过期事实的条目
2. 需复查传播是否完整
3. 关键事实的认定和来源等级
4. 没有任何 P 步骤引用的「必须」级标准
5. 证据版本与交付物版本对不上的
6. 「进行中」且已过截止，或派出后超时仍无回执时间的步骤
7. 快照对比有变化：核心列；以及 A 表「状态 + 版本号 + 确认日期」、D 表「状态 + 谁拍板」、关口一放行标记
8. A 表状态与 专职·流程QA 原始回执不一致；同一 A 编号有多行「用户已确认」
9. 变更定级是否符合对象规则（动到大变更对象却没按大变更走）
10. 待确认积压是否超过上限（10 条 / 3 天）
11. 各 A 编号的失败计数（仅提交复核事件）
12. 各表行数单调不减（只增不删的机械检测；编号应连续，缺号报警）

### 判断项（不算硬检查，交独立 bot）
- 方案和计划是否违反约束；自验证方式是否比检查方法松。**唯一交专职·流程QA** 判断，回执原样附上。

### 检查脚本（导出、运行、降级规则、结果写回；全流程只在这里定义）
- **位置**：本机 `/home/box/flow-scripts/check.py`（box 上所有 bot 共用一份）；标准版在「流程治理」本项目仓库 `scripts/check.py`，安装和登记见 skill「参谋长治理」第 11 节。
- **哈希核对**：每次运行后看输出里的「脚本哈希」，与「流程治理」脚本维护表检查脚本在用行的内容哈希比；不一致时本次结果不当检查结果用，仍按「结果写回」原样贴入并注明「脚本哈希与在用行不一致」，按降级方案处理并告诉参谋长。副官读这一行是允许的只读跨项目，只读不写。
- **导出**（只用 Notion 连接器，不用密钥）：每次运行建一个导出目录 `/home/box/flow-scripts/exports/<项目名>/<YYYYMMDD-HHMMSS>/`，用完保留不删（就是快照）。对每张要查的表：
  1. notion-fetch 该数据库，用 `write_to_file` 存下，复制成 `<代号>-db.txt`（代号：F D R S P A，模板表 T、bot 名册 B、skill 维护表 K、脚本维护表 J）；
  2. 用「按状态分组」视图（不带筛选；已实测 view 模式翻页完整，隐藏空组开关不影响），不用「默认（排除…）」；
  3. notion-query-data-sources，`mode: "view"`、该视图、`page_size: 100`，每页 `write_to_file: true`，结果文件原样复制成 `<代号>-p1.txt`、`<代号>-p2.txt`…；`has_more` 为 true 就把 `next_cursor` 作 `start_cursor` 接着取，直到 false；
  4. 写 `manifest.json`：项目名、导出时间、每张表的代号、表名、所用视图 URL。
  不用 rows 模式（没有游标，超过 100 行就取不全）。SQL 只用于抽查（可选；额度小，整个工作区共用）：结果文件存进导出目录并在 manifest 的 `sql` 里登记；额度用完的错误返回也原样存下。
- **运行**：`python3 /home/box/flow-scripts/check.py run --export-dir <导出目录> --prev <上次的 result.json> --out <导出目录>/result.json`。退出码 0 正常、1 有发现、2 降级。脚本只读导出文件和本机文件（SKILL.md、各 bot 的 profile.json），不连 Notion，不写任何东西。
- **降级规则**：导出不完整、视图带筛选类设置、设定正文还原后与登记哈希对不上或有未转义迹象、SQL 不可用，该项一律标「降级」并写明原因，不算不一致，不手工补判。有任一降级项，本次结果即「降级」。
- **结果写回**（固定格式）：在检查日志页面新增一条，依次为：运行时间｜导出目录｜退出码｜脚本终端输出全文（代码块）｜`result.json` 全文（代码块）。由跑脚本的 bot 贴入（「流程治理」是参谋长，其他项目是本项目副官）；一个字不改、不删减、不转述，不另写摘要代替原文，不删旧记录。发现项：副官按本节「每日扫描」四类规则找用户；参谋长按 skill「参谋长治理」第 5 节处理。

### 降级方案（检查脚本跑不通、脚本哈希与在用行不一致、或结果为「降级」时）
- 项目标「降级模式」：在项目页写一行「降级模式：是（原因，日期）」，位置在首行「项目仓库：…」下面一行（没有项目仓库行的项目写在首行）；同时记一条 D。脚本恢复正常、结果不再降级后，把这一行改成「降级模式：否（恢复日期）」，再记一条 D。关口一一屏拍板首行写明。
- 降级只影响第 12 项和哈希核对：这几项在关口一、关口三改为用户直接看 Notion 原始数据，副官只列出要看哪些视图，不给结论。第 1–11 项本来就是人工检查，照常检查并写出结果，不算降级。
- 把「脚本修复」记成影响为高的风险。

## 12. 执行人怎么定
- 写 P 表时就给每一步定执行人，说明里写理由，关口一由用户确认；实施阶段只照表派活，不临场判断。
- 判断顺序：
  1. 要否决别人结果的角色（想法挑刺、QA）一律交独立 bot。
  2. 非用户不可的（付款、实名、对外发布、主观拍板），执行人写用户。
  3. 其他工作副官按工作量判断：零碎小活自己做（代码派给云端代理）；量大、反复出现或需要专门技能的，拆给专职 bot。
- 每次判断（自己做还是拆给专职 bot）都记一条 D，写明理由；参谋长巡检时会检视这些记录，看副官是否因自己做太多而疏于管流程。
- 找专职 bot 的顺序：先查参谋长维护的 bot 名册 → 再找模板库（由参谋长发链接、用户导入）→ 都没有就向参谋长提需求，由参谋长新写设定（只写职责和规矩，不绑定模型或工具），先登记进模板表经用户确认，再从模板创建，名册模板来源填模板名 + 版本号。专职·流程QA、专职·想法挑刺 只有创世例外可由参谋长照 skill「固定bot设定」直接贴设定建，创世后一律从模板表在用行创建。建好前该步挂起。
- 新 bot 跑通后，副官复盘时提议导出成模板，交参谋长记成候选（见 skill「参谋长治理」第 1 节），按流程确认后登记或更新模板表。
- 只有目标、工具、审批方式或时间安排明显不同于现有 bot 时才单独建 bot，否则做成副官的一个 skill。
- 实施中换执行人算中等变更。
- 跨项目：共用的 bot、预算、时间被多个项目同时占用时先来先做；参谋长发现冲突并列方案，一律由用户拍板，没冲突的跨项目安排也由用户拍板。

## 13. 不能裁剪的最小集
1. 用户确认 A 表「必须」级标准
2. 关口三由 专职·流程QA 独立判断
3. 机械检查
4. 不可逆步骤的执行前关口
5. 变更分级

另：关口二第 1、3、6 项不能省。

## 14. 出口
1. 交付，用户确认收到。
2. 有明确终止的：到终止信号就结项，监控中的风险转「已消除」或写「由用户接管」。长期运营的：先定好监控什么、什么触发新一轮、什么情况终止，再挂上监控任务，每次触发走一轮运营轮。
3. 结项复盘，两类沉淀：
   - 用户偏好：先搜共享记忆有无相近条目，有冲突交用户定，经用户同意后才写进共享记忆。
   - 流程改进建议：交给参谋长，由它记成「流程治理」的候选（见 skill「参谋长治理」第 1 节）。
4. 归档：副官删掉自己为该项目建的定时任务，只保留长期运营项目的监控任务；参谋长复盘时核对。

## 15. 运营轮卡片（长期运营项目每次触发）
1. 触发记录：记一条 F 或 D，写明触发原因。
2. 影响评估：按依赖链机械找出受影响条目。
3. 按变更分级处理（大变更照样退回澄清）。
4. 不可逆步骤过执行前关口，其余过关口二。
5. 只对受影响的 A 条目跑回归，专职·流程QA 靠派活单隔离判断。
6. 三行复盘。

## 16. bot 分工
| 角色 | 职责 |
|---|---|
| 副官（每个项目一个，项目主 bot） | 全流程推进；唯一能写表的；不转述检查脚本输出和 专职·流程QA 回执 |
| 专职·想法挑刺 | 澄清阶段挑想法的刺、找关键事实和风险；所有副官和参谋长共用，靠派活单隔离 |
| 专职·流程QA | 起草验收标准；不可逆步骤预审；实施中抽检；关口三独立判断；关口一判断项；所有副官和参谋长共用，靠派活单隔离（只给本单材料、只据派活单判断） |
| 按需专职 bot | 承接量大、反复或需专门技能的工作，到需要时才建（来源顺序见第 12 节）；只交回执，不写表 |
| 检查脚本 | 关口和每日扫描时查导出完整性（含编号缺号、行数减少）和哈希；原始输出由跑脚本的 bot 原样贴进检查日志，不得改动 |
| 无上下文红队评审 | 由发起评审的 bot 每次开无上下文临时子任务，只给被评文件，不建 bot；不与想法挑刺合并（想法挑刺要用户上下文并长期存在，红队要无上下文、临时开） |
| 参谋长（特殊副官，元副官，只有一个） | 按本流程管「流程治理」项目，同样遵守第 0 节；唯一负责修改 skill；维护 bot 名册、skill 维护表、跨项目信息、改进候选；工作日巡检、每周一复盘；建 bot；不接具体项目的活。详见 skill「参谋长治理」 |
| 用户 | 拍板；确认标准、AI 自定的决定、放行条目、裁剪、不可逆步骤；判断主观口味和对外发布 |

## 17. 版本和修改本 skill
- 项目入口时把所用 skill 版本号记成一条 D。进行中的项目只在用户在该项目里明确批准时才升级（参谋长可以提议并写清理由；全流程只在这里定义）。
- 只有参谋长修改本 skill，副官不改。修改记录不写进任何文件（skill、设定正文、脚本、流程文档），统一记在对应维护表；维护表的版本规则（每版一行、在用行唯一、旧行改已废弃）见 skill「参谋长治理」第 3 节。平台上任何 bot 都能写 skill，无法加锁；以「流程治理」项目里的 skill 维护表为准，参谋长巡检时比对哈希，不一致时按 skill「参谋长治理」第 5 节处理（「认可」只登记候选）。
- 修改流程：副官提建议 → 参谋长记成「流程治理」的候选 → 起任务，按 skill「参谋长治理」第 4 节走（澄清 → 设计 → 无上下文红队评审 → 压力测试和触发测试 → 锁标准 → 开发 → 专职·流程QA 验收 → 用户确认 → 安装到本机并核对本机哈希 → 推送本项目仓库并取回核对 → 维护表新增在用行、旧行改已废弃）。
